# Принятые решения, промпты и ограничения

Документ дополняет README: здесь — «почему сделано так», а не «как запустить».

## 1. Главный принцип: модель предлагает, код проверяет

Требование «модель не должна выдумывать характеристики» нельзя закрыть только
промптом: промпт — просьба, а не гарантия. Поэтому в сервисе два независимых
слоя защиты.

**Слой 1 — промпт.** В системном промпте перечислены прямые запреты (числа,
единицы, стандарты, сертификаты, гарантии, превосходные степени), требование
брать значения дословно и возвращать строгий JSON по схеме.

**Слой 2 — детерминированный код** (`app/core/`, `app/pipeline.py`):

| Проверка | Что делает |
| --- | --- |
| Числа-страж (`core/guard.py`) | Извлекает все числа из готового текста и сверяет их с **фактами** (производитель, описание, specs) по целым токенам. Цифры из названия/артикула подтверждают текст только если в фразе есть сам токен модели (МП3-У), а не голое «класс точности 3». |
| Словарь утверждений (`core/guard.py`) | Проверяет маркеры материалов, стандартов (ГОСТ, DIN, ISO), сертификатов, гарантий и взрывозащиты (в т.ч. взрывоопасн*, EXI, Exd, ATEX). Утверждение, которого нет во входе, удаляется вместе с предложением. |
| Характеристики (`core/builder.py`) | Модель выбирает, какие характеристики важны, но **значение всегда берётся из входного JSON дословно**, а подпись проверяется на соответствие ключу: «Гарантия» с ключом «Масса» превращается в «Масса». Если значения нет — `данных нет`. |
| Обязательные поля (`core/profiles.py`) | Для ключевых характеристик семейства приборов отсутствие фиксируется явно, а не замалчивается. |
| Длины и количество (`pipeline.collect_problems`) | `seo_title ≤ 70`, `seo_description 800–1200`, 3–5 запросов, непустой коммерческий блок. |

Такой порядок даёт честный ответ на вопрос «а если модель всё-таки соврёт».
В характеристиках соврать нельзя структурно: значения туда не записываются из
ответа модели, а подпись сверяется с ключом. В свободном тексте работают числа-страж
и словарь утверждений — оба эвристические: они ловят новые числа и типовые
технические заявления, но не распознают перефразированное утверждение без
ключевых слов. Это осознанный компромисс: детерминированная проверка дешёвая и
объяснимая, полная семантическая верификация вынесена в план улучшений.

## 2. Профили полноты вместо жёсткой схемы товара

Жёсткая схема («все поля обязательны») ломается на первом же приборе другого
типа: у манометра нет питания и интерфейсов, у газоанализатора нет резьбы.
Поэтому профиль — это подсказка:

- 5 семейств (манометр, термопреобразователь, газоанализатор, расходомер,
  преобразователь давления) + универсальный профиль;
- семейство определяется по ключевым словам в названии и описании;
- если не угадали — работает `generic`, сервис не падает;
- отсутствующие поля попадают в блок «Требует уточнения» и в промпт как список
  того, что нельзя упоминать.

Это же покрывает требование «если данных недостаточно, сообщать, какие поля
отсутствуют»: ответ формируется до вызова модели и не зависит от её фантазии.

## 3. Один repair-проход, потом детерминированная доводка

Схема обработки ответа:

1. разбор JSON (снимаем ```-обёртки, ищем объект в тексте);
2. нормализация (пробелы, маркеры списков, кавычки, регистр запросов);
3. проверки `collect_problems`;
4. если есть нарушения — **один** повторный запрос с перечнем проблем;
5. если и после этого нарушения остались — детерминированные правки:
   обрезка заголовка по границе слова, обрезка/добивка описания, добор
   запросов из названия товара;
6. всё, что не удалось исправить, — в `warnings` карточки, а не в тишину.

Почему один проход: каждый лишний вызов стоит денег и времени, а второй почти
не улучшает результат. Почему добивка описания нейтральными фразами: требование
к объёму формальное, а добавлять факты ради объёма нельзя — поэтому текст
добивается фразами без единого числа и без утверждений о приборе.

## 4. Промпт: структура и эволюция

Файлы: `app/prompts/system.md` (правила и схема), `app/prompts/user.md`
(данные товара, семейство, список отсутствующих полей).

Ключевые приёмы:

- **JSON-схема в промпте + `response_format` в API.** Для провайдеров, которые
  не поддерживают `response_format`, клиент автоматически повторяет запрос без
  него (текст всё равно требует JSON).
- **`source_key` вместо значения.** Модель возвращает ссылку на ключ входных
  данных, а не само значение. Это и убирает выдумывание, и упрощает маппинг:
  даже если модель переименовала характеристику для таблицы, значение берётся
  по ключу.
- **Явный список того, чего нет.** Модель склонна «дописывать очевидное»:
  манометру приписывают питание, датчику — интерфейс. Прямой запрет с перечнем
  отсутствующих полей снижает это заметно сильнее, чем общая формулировка
  «не выдумывай».
- **Запрет превосходных степеней и сравнений.** B2B-карточка не должна
  содержать маркетинговых утверждений, которые невозможно подтвердить.
- **Точные числа и единицы в исходном написании.** Иначе числа-страж начинает
  срабатывать на «1.5» против «1,5».

Что менялось по ходу: в первой версии модель возвращала характеристики парами
«название → значение», и в них попадали правдоподобные, но несуществующие
параметры; после перехода на `source_key` такие случаи исчезли. Вторая правка —
явное требование «не упоминать отсутствующие поля»: без него модель
пересказывала типовой паспорт прибора.

Третья итерация — по результатам реального прогона:

- заголовок выбирал одно значение из списка равноправных (у ДТС035 стояло
  «НСХ Pt100», хотя поддерживаются шесть НСХ) — добавили запрет выбирать одно
  значение из перечисления;
- в заголовке оказалось число без пояснения («МП3-У 100 мм») и слово
  «характеристики» — добавили требования «число только с пояснением» и «без
  слов-заполнителей»;
- в карточке с малым объёмом данных факты повторялись разными словами —
  добавили требование не повторяться.

После этих правок все три примера укладываются в требования без единого
предупреждения проверок.

## 5. Ключи API

Три способа, все без попадания ключа в репозиторий:

1. поле в веб-интерфейсе (тип `password` с переключателем видимости) — ключ
   уходит только в теле запроса на локальный сервер и живёт в памяти процесса;
2. `.env` (в `.gitignore`, есть `.env.example`);
3. переменные окружения.

Дополнительно: `api_key` исключён из `repr` модели запроса, не логируется,
в тексте ошибок провайдера вырезается (`redact`), в ответ API не возвращается
(это закреплено тестом `test_api_key_is_never_echoed_back`).

## 6. Провайдер-агностичность

`openai`, `anthropic`, `google`, `openai_compatible` (любой endpoint с
OpenAI-совместимым `/chat/completions`), `mock`. Плюс `LLM_USER_AGENT` и
`LLM_EXTRA_HEADERS`: корпоративные шлюзы часто требуют собственный заголовок
маршрутизации.

`mock` — не заглушка ради галочки: он собирает карточку из входных данных по
шаблону и позволяет проверить весь конвейер без ключа и без сети (на нём же
работают сквозные тесты).

## 7. Почему FastAPI и статика без сборки

Задание ограничивает время и просит простой запуск. Один процесс `uvicorn`,
никакого npm и сборки: `static/` — три файла, форма на нативном JS. При этом
`/docs` даёт готовую OpenAPI-документацию бесплатно, а тот же движок доступен
из CLI — удобно и для контент-менеджера, и для пакетной обработки.

## 8. Ограничения решения

- Числа-страж сравнивает числа как токены и не сверяет единицы: «0,7 кг» и
  «0,7 г» для него одно и то же число, если оно есть во входе.
- Словарь утверждений — список маркеров, а не понимание смысла: он не поймает
  «корпус не боится агрессивных сред», если такой фразы нет в словаре.
- Профили полноты покрывают 5 семейств; для остальных работает универсальный,
  и подсказки менее точные.
- Числа-страж не сверяет единицы (`0,7 кг` vs `0,7 г`) и не понимает семантику
  «это класс точности»; он лишь не даёт цифрам из артикула подтверждать
  произвольные фразы без токена модели.
- Описание может быть добито нейтральными фразами до 800 символов — формально
  требование выполнено, но пользы такой текст не добавляет; в карточке об этом
  есть предупреждение.
- Нет кэша, истории, базы данных и фоновых задач: каждый запрос — отдельный
  вызов модели. Пакетная обработка — через CLI.
- Нет стриминга ответа: для карточки 1–2 КБ текста это не критично.
- Оценка качества текста не автоматизирована: длины и отсутствие выдуманных
  чисел проверяются кодом, стиль — глазами контент-менеджера.
- Repair-проход один; при нестабильном провайдере можно увеличить
  `max_repairs` в вызове `generate_card`.

## 9. Что улучшить дальше

1. **Проверка единиц измерения** — сопоставлять число вместе с единицей
   (`0,7 кг` vs `0,7 г`), а не только число.
2. **Семантическая проверка утверждений** — второй проход моделью-судьёй
   («есть ли в тексте утверждение, которого нет в данных»), с обязательным
   детерминированным подтверждением.
3. **Пакетная обработка** — очередь, обработка каталога, прогресс, ретраи.
4. **Кэш по хэшу входных данных** — снижает стоимость повторных прогонов.
5. **Обратная связь контент-менеджера** — «принять/отклонить правку» с
   сохранением правок как few-shot примеров.
6. **Расширение профилей** — по каталогу заказчика, с весами полей.
7. **Экспорт в формат CMS** — выгрузка в CSV/XML фида, а не только Markdown.
8. **Тесты на реальных ответах модели** — записанные ответы (record/replay),
   чтобы ловить регрессии промпта без расходов на API.

## 10. Что изменилось после независимого ревью

Проект прошёл отдельный проход ревью «свежим взглядом». Что исправлено:

| Находка | Исправление |
| --- | --- |
| Ключ из `.env` уходил на произвольный `base_url` из запроса | Ключ используется только для endpoint'а из `.env`; при своём `base_url` ключ обязан прийти в запросе |
| SSRF через `base_url` | Валидация адреса: `https` для внешних хостов, внутренние и служебные адреса отклоняются |
| Число «10» подтверждалось числом «100» | Сравнение по целым числовым токенам |
| Проверялись только числа | Добавлен словарь технических утверждений |
| Значение под чужой подписью | Подпись проверяется на соответствие ключу характеристики |
| `sanitize` склеивал абзацы и рвал десятичные числа | Разбиение на предложения не режет «0.7», абзацы сохраняются |
| Пустой `seo_title` оставался пустым | Подставляется название товара |
| Запросы не проверялись стражем | Неподтверждённые запросы удаляются и добиваются безопасными |
| Сбой repair-прохода выбрасывал валидную карточку | Первая версия сохраняется, в предупреждениях — причина |
| Предупреждение перечисляло уже исправленные проблемы | Проблемы пересчитываются после доводки |
| «Данных нет» для того, что есть в описании | Наличие поля учитывается и по тексту техпаспорта |
| Нет лимитов на размер входа | Ограничения на длину полей и число характеристик |
| Инъекция через ``` в описании товара | Блок кода в промпте экранируется |
| Ключ Google в query string | Передаётся заголовком `x-goog-api-key` |
| Ошибки валидации повторяли присланный ключ | Обработчик 422 не возвращает исходные значения |

## 11. Три формата вывода

Один и тот же контент отдаётся в трёх видах, потому что у них разные потребители:

| Формат | Кому | Зачем |
| --- | --- | --- |
| Markdown | контент-менеджер | проверить и скопировать по блокам; сохраняет структуру таблицы характеристик |
| Обычный текст | контент-менеджер, CMS | вставляется в текстовое поле без разметки, без `#` и `|` |
| JSON | интеграция | пакетная выгрузка в CMS/фид, когда карточек тысячи |

Дублирование контента в трёх видах сознательное: конвертировать Markdown в чистый
текст «на лету» в браузере — лишний слой, который ломается на таблицах, а JSON нужен
машине, а не человеку. Рендер один (`app/render.py`), поэтому форматы не расходятся.

## 12. Ключ API: серверная сессия вместо браузерного хранилища

Требование «не вводить ключ при каждом запросе» конфликтует с «ключ не должен
утекать». Рассмотренные варианты:

| Вариант | Почему нет |
| --- | --- |
| `localStorage` | читается любым скриптом на странице; на общем компьютере ключ остаётся навсегда |
| `sessionStorage` | умирает при перезагрузке вкладки — не решает задачу |
| файл на диске из HTTP-запроса | запись секрета по запросу — плохая практика (и лишний вектор атаки) |
| **серверная сессия (выбрано)** | ключ в памяти процесса, браузер получает только непрозрачный id в HttpOnly-cookie |

Что это даёт: JS на странице не может прочитать ключ, `GET /api/session` возвращает
лишь `{has_key, masked: "••••a1b2"}`, в логи и ответы ключ не попадает. Сессия живёт
12 часов и до перезапуска сервера, лимит — 200 сессий, «Забыть ключ» удаляет сразу.

Цена решения: после рестарта сервера ключ нужно ввести заново. Для прототипа это
приемлемо; для продакшена правильный путь — секрет-менеджер (Vault, AWS Secrets
Manager) и сервисная учётная запись, а не ключ пользователя.

Приоритет источников ключа: **ключ в запросе → ключ сессии → ключ из `.env`**. Ключ
сессии отправляется только на тот endpoint, с которым его сохранили: иначе подменой
`base_url` его можно было бы увести на чужой хост.

## 13. Доработка после ревью сдачи

| Находка | Исправление |
| --- | --- |
| 3 теста падали без DNS (`example.com`) | фикстура `public_dns` мокает `getaddrinfo` |
| Mock выдумывал доставку по России | филлер заменён на нейтральную фразу без фактов |
| Цифра из артикула МП3-У подтверждала «класс точности 3» | проверка идёт по `fact_text()`; цифры из имени — только с токеном модели |
| Не ловились «взрывоопасн*» / EXI | расширен словарь маркеров |
| Incomplete уходил в `generic` | добавлен профиль преобразователя давления |

## 14. Список моделей

Названия моделей меняются чаще, чем код, поэтому список собирается из двух источников:
справочник в `app/model_catalog.py` (работает без ключа и без сети) и загрузка реального
списка у провайдера по кнопке ⟳ (кэш на час, ключ не сохраняется). Результат
объединяется: то, что вернул провайдер, идёт первым, справочник дополняет.

Если провайдер недоступен или ключ неверный — интерфейс не падает, а показывает
справочник и текстом объясняет причину. Поле модели остаётся обычным вводом, так что
своё название можно указать всегда.
