# Карточка товара — AI-помощник для контент-менеджера

Прототип сервиса: получает данные контрольно-измерительного прибора (JSON или веб-форма),
отдаёт их в LLM и возвращает черновик карточки товара для B2B-интернет-магазина:
SEO-заголовок, SEO-описание, структурированные характеристики, поисковые запросы и
коммерческий блок для менеджера.

Главное свойство: **сервис не выдумывает технические характеристики**. Всё, чего нет
во входных данных, помечается как «данных нет», а числа в готовом тексте сверяются
с входом кодом, а не доверием к модели.

---

## Быстрый старт

Нужен Python 3.10+.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env        # вставьте ключ в LLM_API_KEY (или введите его в форме)
uvicorn app.main:app --reload
```

Откройте <http://127.0.0.1:8000>.

Ключ можно вообще не класть в `.env`: в интерфейсе есть поле «Ключ API» с маскировкой
и переключателем видимости. Ключ уходит только в текущем запросе, не сохраняется ни в
браузере, ни на сервере, ни в логах.

**Хотите посмотреть без ключа?** Выберите провайдера «Офлайн-демо (без модели)» — карточка
соберётся по детерминированному шаблону из входных данных. Это же режим используют тесты.

### Проверка установки

```bash
pytest -q          # 36 тестов, сеть не нужна
```

## Как пользоваться

1. Вставьте JSON товара в левую панель (или выберите готовый пример в списке).
2. Нажмите **«Проверить данные»** — сервис покажет, каких характеристик не хватает.
   Это делается локально, без обращения к модели.
3. Нажмите **«Сформировать карточку»**.
4. Результат: вкладки «Карточка» (Markdown) и «JSON», кнопки «Копировать» и «Скачать .md».

Формат входных данных — ровно как в задании:

```json
{
  "name": "Манометр показывающий МП3-У",
  "manufacturer": "Манотомь",
  "specs": {
    "Диапазон измерений": "0–100 кгс/см²",
    "Класс точности": "1,5",
    "Присоединение": "G1/2",
    "Диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Дополнительно `specs` принимается списком пар — так удобнее выгружать из таблицы:

```json
"specs": [{"name": "Класс точности", "value": "1,5"}]
```

Пустые значения и `null` отбрасываются, лишние поля игнорируются, числа приводятся к
строкам.

## Командная строка

Тот же конвейер без сервера — удобно для пакетной обработки:

```bash
# офлайн-демо без ключа
python -m app.cli examples/mp3-u-manometer.json --provider mock --out output

# реальная модель (провайдер и ключ берутся из .env)
python -m app.cli examples/*.json --out output

# только проверка полноты данных
python -m app.cli examples/dts035-thermometer.json --analyze-only
```

Файлы `output/<имя>.md` и `output/<имя>.json` перезаписываются при повторном запуске.

## Как это устроено

```
JSON → разбор и нормализация (Pydantic)
     → проверка полноты по профилю семейства приборов   ← без LLM
     → сборка промпта (правила + данные + список пробелов)
     → вызов LLM через адаптер провайдера
     → разбор JSON, нормализация ответа
     → проверки: длины, количества, числа-страж          ← без LLM
     → один repair-проход при нарушениях
     → детерминированная доводка + предупреждения
     → Markdown + JSON для контент-менеджера
```

### Почему модель не выдумывает характеристики

Промпт — просьба, а не гарантия, поэтому защита двухслойная.

1. **Промпт** перечисляет прямые запреты: числа, единицы, стандарты, сертификаты,
   гарантии, превосходные степени, сравнения с брендами. Отдельным пунктом —
   «не упоминай характеристики, которых нет» (список отсутствующих полей передаётся
   в промпт явно).
2. **Код проверяет результат:**
   - все числа из заголовка, описания и коммерческого блока сверяются с входными
     данными; число, которого нет во входе, удаляется вместе с предложением, а в
     карточку добавляется предупреждение;
   - значения характеристик **не берутся из ответа модели** — модель возвращает
     `source_key`, а значение подставляется из входного JSON дословно; если ключа
     нет, в карточке будет «данных нет»;
   - для ключевых полей семейства приборов отсутствие фиксируется явно
     (`missing_data`), а не замалчивается.

Подробнее о решениях и компромиссах — в [`docs/DECISIONS.md`](docs/DECISIONS.md).

### Промпты

| Файл | Назначение |
| --- | --- |
| [`app/prompts/system.md`](app/prompts/system.md) | роль, запреты, требования к полям, JSON-схема ответа |
| [`app/prompts/user.md`](app/prompts/user.md) | данные товара, семейство прибора, список отсутствующих полей |

Ключевой приём — **`source_key`**: модель не пишет значение характеристики, а
ссылается на ключ из `specs`. Это убирает самый частый вид галлюцинации —
правдоподобный, но неверный параметр.

При нарушении требований (длина, количество запросов, лишние числа) сервис делает
один повторный запрос с перечнем конкретных проблем и только потом правит
результат детерминированно.

### Профили полноты

Четыре семейства — манометр, термопреобразователь, газоанализатор, расходомер — плюс
универсальный профиль. Семейство определяется по названию и описанию; для незнакомого
прибора сервис продолжает работать, просто подсказки менее точные.

## Провайдеры

| Провайдер | `LLM_PROVIDER` | Что задать |
| --- | --- | --- |
| OpenAI | `openai` | `LLM_API_KEY`, при необходимости `LLM_MODEL` |
| Anthropic Claude | `anthropic` | `LLM_API_KEY`, `LLM_MODEL` |
| Google Gemini | `google` | `LLM_API_KEY`, `LLM_MODEL` |
| Любой OpenAI-совместимый endpoint | `openai_compatible` | `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY` |
| Офлайн-демо без модели | `mock` | ничего |

Переменные окружения (см. `.env.example`):

| Переменная | Назначение |
| --- | --- |
| `LLM_PROVIDER` | провайдер по умолчанию |
| `LLM_API_KEY` | ключ; можно не задавать, если вводите в форме |
| `LLM_MODEL` | модель |
| `LLM_BASE_URL` | адрес endpoint для `openai_compatible` |
| `LLM_TIMEOUT` | таймаут запроса, секунды (по умолчанию 60) |
| `LLM_TEMPERATURE` | температура (по умолчанию 0.2) |
| `LLM_USER_AGENT` | User-Agent клиента |
| `LLM_EXTRA_HEADERS` | JSON-объект с дополнительными заголовками для шлюзов |

Пример для OpenAI-совместимого шлюза:

```bash
LLM_PROVIDER=openai_compatible
LLM_BASE_URL=https://opencode.ai/inference/go/openai/v1
LLM_MODEL=deepseek-v4.1-flash
LLM_API_KEY=...
LLM_EXTRA_HEADERS={"x-opencode-session":"product-card-local"}
```

> Для публичных провайдеров `LLM_EXTRA_HEADERS` не нужен — это escape hatch для
> корпоративных прокси и шлюзов.

## API

| Метод | Путь | Что делает |
| --- | --- | --- |
| `GET` | `/` | веб-интерфейс |
| `GET` | `/api/providers` | список провайдеров и моделей по умолчанию |
| `GET` | `/api/examples` | примеры из каталога `examples/` |
| `POST` | `/api/analyze` | проверка полноты данных без обращения к модели |
| `POST` | `/api/generate` | генерация карточки |
| `GET` | `/docs` | OpenAPI-документация |

```bash
curl -s http://127.0.0.1:8000/api/generate \
  -H 'Content-Type: application/json' \
  -d '{
        "product": {
          "name": "Манометр МП3-У",
          "manufacturer": "Манотомь",
          "specs": {"Диаметр корпуса": "100 мм"},
          "description": "Прибор для измерения избыточного давления."
        },
        "llm": {"provider": "mock"}
      }'
```

Ответ содержит `card` (структурированная карточка), `markdown` (готовый текст),
`json` (та же карточка строкой) и `meta` (провайдер, модель, время, число обращений).

Ошибки: `422` — некорректные данные товара (с указанием поля), `400` — неизвестный
провайдер или не задан ключ, `502` — ошибка провайдера.

## Безопасность

- ключ не хранится в коде и не коммитится: `.env` в `.gitignore`, есть `.env.example`;
- ключ из формы живёт только в памяти процесса на время запроса;
- ключ вырезается из текста ошибок провайдера (`redact`) и не попадает в логи;
- в ответе API ключ не возвращается (покрыто тестом).

## Ограничения и что дальше

Кратко: числа-страж сравнивает числа подстрокой и не проверяет единицы; профили
покрывают четыре семейства; описание может добиваться нейтральными фразами до
нижней границы объёма; нет кэша, очередей и истории. Полный список и план
улучшений — в [`docs/DECISIONS.md`](docs/DECISIONS.md), разделы 8 и 9.
